  FORK 1: FORGECODE-FORK
================================================================================

EPIC ID: eco-fork-001
TITLE: Custom Providers & Subagent Management Infrastructure
TIMELINE: Weeks 1-6 (Phase 1: Weeks 1-3, Phase 2: Weeks 4-6)
EFFORT: 18-24 parallel subagents, 6 work packages, 72-99 tool calls

VISION:
Transform AgilePlus from a spec-driven engine into a composable agent 
orchestration platform where each provider (Claude, Grok, local models) 
and each agent type can be independently registered, versioned, and routed.

KEY DELIVERABLES:
- forgecode-providers crate (Provider trait, registry, 3 implementations)
- agileplus-provider-cli integration (provider + spawn-agent subcommands)
- forgecode-agent-dispatch gRPC service
- Provider audit trail with hash-chain verification
- Provider development guide + example custom provider

WORK PACKAGES:
WP01: Provider Trait & Registry (400 LOC, 12-15 calls) — Foundation
WP02: Claude Provider Implementation (350 LOC, 10-12 calls) — Multi-model routing
WP03: Local Provider + Ollama (280 LOC, 8-10 calls) — Offline inference
WP04: Provider-Aware Subagent Spawning (420 LOC, 14-16 calls) — Agent dispatch
WP05: Capability Discovery & Routing (380 LOC, 11-13 calls) — Smart routing
WP06: Provider Performance Metrics (340 LOC, 10-12 calls) — Feedback loop

SUCCESS METRICS:
✓ Provider registry with ≥3 implementations, thread-safe
✓ Subagent spawning: agileplus spawn-agent WP01 --provider claude --model opus
✓ Capability discovery: agileplus provider list/show
✓ Audit trail: hash-chained provider calls with token counts
✓ Automatic fallback on provider failure (Opus → Sonnet)
✓ ≥90% test coverage; zero clippy warnings

  FORK 3: BIFROST-ROUTING
================================================================================

EPIC ID: eco-fork-003
TITLE: LLM Routing Infrastructure with Model Selection & Cost Optimization
TIMELINE: Weeks 1-6 (Phase 1: Weeks 1-2, Phase 2: Weeks 3-4)
EFFORT: 16-20 parallel subagents, 6 work packages, 72-90 tool calls

VISION:
Transform LLM selection from manual ("use Opus for everything") into 
data-driven ("route to Haiku/Sonnet/Opus based on cost/latency/quality").

KEY DELIVERABLES:
- bifrost-routing-core (routing engine, request classifier, SLA enforcement)
- bifrost-routing-models (LLM model definitions, cost/latency metadata)
- bifrost-routing-analytics (cost tracking, A/B metrics, performance analysis)
- bifrost-routing-cli integration (routing management, SLA tuning)
- Model selection guide, cost optimization strategies, SLA tuning docs

WORK PACKAGES:
WP01: Request Classifier & Workload Inference (380 LOC, 11-13 calls) — Classification
WP02: LLM Model Registry & Capability Metadata (300 LOC, 8-10 calls) — Model definitions
WP03: Token-Aware & Workload-Based Selection (400 LOC, 12-14 calls) — Smart selection
WP04: SLA Enforcement & Latency Timeout (320 LOC, 9-11 calls) — Performance SLAs
WP05: Cost Tracking & Budget Enforcement (360 LOC, 10-12 calls) — Cost control
WP06: A/B Testing & Shadow Routing (340 LOC, 10-12 calls) — Model evaluation

SUCCESS METRICS:
✓ Classifier: "write a function" → code, "analyze sales data" → analysis
✓ Token-aware: <500 tokens → Haiku, 500-2K → Sonnet, >2K → Opus
✓ Cost optimization: 30-40% cost reduction vs baseline (all Opus)
✓ SLA enforcement: latency SLA per workload; failover if breached
✓ Budget enforcement: 429 + clear error if user exceeds monthly cap
✓ A/B testing: shadow route to new model; collect metrics without affecting traffic
✓ ≥90% test coverage

================================================================================
  KEY DESIGN PATTERNS & CONSTRAINTS
================================================================================

FORGECODE-FORK:
  ✓ Provider trait must be minimal (invoke, stream, capabilities)
  ✓ Registry thread-safe (Arc + RwLock)
  ✓ No inter-provider dependencies
  ✓ All providers support fallback + error handling
  ✓ Audit trail hash-chained for integrity

PHENOTYPE-ROUTER-MONITOR:
  ✓ Single-threaded router core (tokio async)
  ✓ In-memory rate limiting (no distributed coordination Phase 1)
  ✓ TOML configuration (schema validation at startup)
  ✓ Health checks independent per backend
  ✓ Prometheus metrics format (UTF-8, standard names)

BIFROST-ROUTING:
  ✓ Classifier heuristic-based (no ML Phase 1)
  ✓ Token counting approximate (length-based)
  ✓ Workload types fixed: code, analysis, writing, retrieval
  ✓ SLA per workload (not per user Phase 1)
  ✓ Cost tracking granular (per request, queryable)
